## Operational Triage Guide: Pinpointing vLLM & Ray Code Hangs
Target Infrastructure: Grace-Hopper (GH200) Nodes running with User-Space Forward Compatibility
Active Baseline: Debug Level 4 Diagnostics (NCCL_DEBUG=INFO, py-spy, PyTorch Flight Recorder)
------------------------------
## 1. The Core Strategy: Bypassing the Driver Layer
On this platform, attempts to trigger standard driver-level core dumps via the /proc filesystem or cuda-gdb are blocked by the kernel due to a user-to-kernel context mismatch, outputting a Late attach error in cuda.log.
Ignore the driver errors. You do not need them. Because Debug Level 4 is active, you have high-density user-space logs (py-spy and PyTorch Flight Recorder) that map the execution state straight to the exact file and line number in the codebase.
------------------------------
## 2. Step 1: Isolate "Patient Zero" (The Culprit Node)
When a collective communication hang (such as an NCCL deadlock) happens, every node in the cluster flatlines at once. The first step is to isolate the node that initiated the freeze from the nodes that are simply frozen on a network barrier waiting for a peer (the Victims).
Open the active node_{node}_threads.txt files generated by py-spy for all nodes side-by-side:

* The Victim Nodes: 100% of their active worker threads will be trapped inside the collective communication wrappers:

File "vllm/distributed/device_communicators/pynccl.py", line 143, in all_reduce
File "torch/distributed/distributed_c10d.py", line XX, in all_reduce

* Patient Zero: This node's stack trace will not be waiting inside pynccl.py or an all_reduce call. It will be executing local compute layers, memory allocations, or standard python event loops.

Isolate this node immediately. All subsequent steps in this guide must be performed exclusively on Patient Zero's log files.
------------------------------
## 3. Step 2: Extracting the Exact Line Number of the Hang
Once Patient Zero is isolated, you can read the log artifacts to pull the literal file paths and source lines causing the deadlock.
## Path A: Finding the Location via py-spy
Open Patient Zero's node_{node}_threads.txt. Locate the thread marked (active). Read from the top frame downwards. py-spy takes a live memory map of the interpreter, showing you exactly where the instruction pointer is pinned at that second:

Thread 70379566749280 (active):
    forward (vllm/model_executor/models/llama.py:118)
    _run_once (asyncio/base_events.py:42)


* The Code Location: vllm/model_executor/models/llama.py, Line 118.
* Triage Analysis: The engine is stuck on a local model execution step before it could even hit a communication boundary. Search Line 118 for heavy CPU functions or non-asynchronous blockers (like os.stat or large tensor reshaping operations) that are starving vLLM's single-threaded event loop.

## Path B: Finding the Location via PyTorch Flight Recorder
If the thread is inside a collective, but the hang is due to an internal sequence desync, open the torch-nccl-node-* files on the shared drive. Because your environment compiles with export TORCH_FR_CPP_STACK=1, it maps the execution straight down through Python into the backend C++ layer:

[Flight Recorder Trace - Rank 0]
Collective ID: 5410
Op: ALL_REDUCE
Status: STALLED
Python Stack:
  vllm/distributed/device_communicators/pynccl.py:143
C++ Stack:
  at::native::ncclKernel_AllReduce(at::Tensor&, ...)


   1. Find the current Collective ID (e.g., 5410).
   2. Compare this ID across nodes. If Rank 0 is stalled on ID 5410, but Rank 1's Flight Recorder shows it is already waiting on ID 5411, you have found a Sequence ID Mismatch.
   3. The Code Location: Open your codebase and inspect any dynamic padding rules, conditional branching (if/else), or dynamic shape calculations executed right around the layer handling that specific all_reduce tensor to see why Rank 0 skipped an operational frame.

## Path C: Finding the Location via nccl-debug.log
Because NCCL_DEBUG_SUBSYS=INIT,BOOTSTRAP,ENV,GRAPH,COLL,NET is exported at Level 4, the trailing edge of the nccl-debug.log file prints the exact internal file coordinates inside the NVIDIA NCCL source code:

[node01:204851] NCCL INFO graph/search.cc:412 -> Topology search stalled


* The Code Location: graph/search.cc, Line 412.
* Triage Analysis: If the trace ends inside a graph/search.cc or init.cc line, the hang is occurring during vLLM's initial CUDA Graph capture phase at startup. If it ends inside transport/ofi_plugin.cc, your underlying network fabric provider (CXI) dropped an execution packet at the kernel level.
