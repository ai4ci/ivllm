## Resolved

- **Console log tailing dropped/garbled lines** (missing `-n` history window on `tail -f`, raw `\r` progress bars overwriting console lines, chunk-not-line stdout echoing in `runRemote`, and a racy double-tail handoff between job startup and `watchLog`). Fixed by: explicit `-a`/from-now flag on `ivllm-show-log.sh` replacing the ambiguous default `tail -f` window; `stdbuf -oL tr '\r' '\n'` normalization in both tail pipelines; line-buffering in `SshRemoteOps.runRemote()`; and removing `requestStart()`'s own log monitor in favour of a single `watchLog()` call in `cmdConnect`/`cmdCancel` gated by status polling (`isStarting`/`isStopped`) instead of log-text markers.

- **`wait_report()` couldn't detect or propagate a crashing vLLM process's real exit code** (`src/engine/lib/utils.sh`). `wait_report()` is the last command in `run_head_vllm.sh`; its own exit status becomes the script's exit status, which `srun` mirrors, which `wait_all`/`setup_traps`'s EXIT trap (`tidy_up`) receives as the real crash/exit code. The old loop only ever did `kill -0 "$pid"` — never `wait "$pid"`. Since `$pid` is a direct child of that same shell, once it exits it becomes a zombie, and `kill -0` still succeeds on a zombie (the PID stays allocated until the parent reaps it) — so the loop could never reliably notice death, let alone capture the real exit code. In practice this meant a genuine crash was never caught via the fast, correct exit-trap path, and instead surfaced only later via `monitor_head`'s independent idle-timeout detection, which routes through `tidy_up`'s `201` ("user cancel or idle timeout") branch — a branch that does **not** call `capture_job_diagnostics`. Net effect: crash diagnostics were silently never captured, misreported as an idle shutdown instead.
  Fixed by checking `/proc/$pid/stat`'s state field for `Z` (zombie) instead of trusting `kill -0`, then doing a final `wait "$pid"; return $?` to reap it and propagate the real exit code.
  Verified by `tests/bash/sandboxed/test-wait-report.sh` (`wait_report_propagates_crash_exit_code`, `wait_report_propagates_clean_exit_code`) — both currently pass against the fixed code.

- **`copyDirectory()` didn't reliably make the bootstrapped remote engine directory group-writable** (`src/ops/SshRemoteOps.ts`). Two related problems, found while investigating a report that one user's `ivllm` run left `$projectDir/engine/lib` un-writable for other users in the same HPC project group:
  1. `rsync -a` (archive mode, which implies `--perms`) copies the *local* machine's exact permission bits onto the shared remote directory on every bootstrap sync (`IsambardBareMetalBackend.bootstrap()` calls this unconditionally). Whoever's local umask/checkout happened to be more restrictive would silently clobber the shared directory's group-writability for everyone else.
  2. Directories and files needed different fixes. Directories: `--no-perms --no-owner --no-group` (stop copying source permission bits) + `--rsync-path 'umask 002 && rsync'` (force the *receiving* rsync process's umask, scoped only to this transfer via `--rsync-path`, not global shell config) is sufficient — a newly-created directory gets a fresh default request (`0777`) that a `002` umask correctly masks to `0775`. Regular files are different: without `--perms`, rsync (like plain `cp` without `-p`) uses the *source file's own mode bits* as the base request, and a umask can only strip bits from that, never add ones the source lacked — so a file that's locally `644` (no group-write — exactly what a fresh `git clone` produces under a normal `022` umask, since git only tracks the executable bit) stayed `644` on the destination no matter what umask the `--rsync-path` trick forced. Confirmed as standard POSIX copy semantics (reproduces identically with plain `cp`), not an rsync quirk, and confirmed to matter in practice only when the pushing machine's local checkout isn't already group-writable (invisible in an environment where it happens to be, e.g. this sandbox's own `775`/`664` files — masking the gap during earlier real-world validation).
  Fixed by following the rsync (on `'up'` transfers only) with an explicit `chmod -R g+rwX "${remotePath}"` over the same SSH connection — deterministic and independent of source mode or any umask timing, closing the gap for both directories and files uniformly. `copyFile()` (used for uploading a job's `vllm.yaml`) was separately re-implemented to stream via `umask 002 && cat > remoteFile` instead of `scp` (which has no `--rsync-path`-equivalent hook), so it was never subject to the file-level gap.
  Verified by `tests/unit/SshRemoteOps.test.ts` (all 3 tests passing): `copyDirectory` leaves both the destination directory *and* files group-writable even under a restrictive local umask with a source file that itself lacks the bit, and `copyFile` likewise.

- **`bun:test` cannot reliably exercise umask-dependent child-process behaviour** (testing-infrastructure finding, not a product bug — kept here for the record since it cost real investigation time and could recur). While building the `copyDirectory` permission tests above, a test asserting group-write via the `--rsync-path 'umask 002 && rsync'` mechanism *alone* (before the `chmod -R g+rwX` fix existed) consistently failed under `bun test` but passed when the identical code (same `SshRemoteOps` class, same fake-`ssh`-on-PATH fixture used in `tests/unit/SshRemoteOps.test.ts`, same `process.umask(0o022)` simulation) was run via plain `bun run` instead — and the `bun run` result matched real Isambard behaviour. Conclusion: Bun's test runner (`1.3.14`) does something that breaks umask inheritance from a test's `process.umask()` call down to a spawned child process; the exact internal mechanism wasn't identified further. This is no longer blocking anything — the shipped fix (explicit `chmod -R g+rwX`) is deterministic and untroubled by this, so all three tests in `tests/unit/SshRemoteOps.test.ts` pass reliably under `bun:test`. Documented here in case a *future* test ever needs to depend on umask propagating to a spawned child under `bun test` — that will hit the same wall.
