- **MiniMax-M3-AWQ-INT4 (`logs/mmax3q/20260903_152700/`): silent, undetected 5-minute startup hang, EngineCore stuck in `torch.cuda._lazy_init()` — unrelated to the GLM-5.2 shm_broadcast hang saga below, root cause found and a fix drafted, 2026-09-03.** Model loaded fine (weights at 15:20:46, CUDA graphs captured 15:21:23) but the job never reached `/health`; `report_memory()`'s periodic snapshot showed GPU util pinned at 0% and `EngineCore` RSS slowly creeping (899M→2188M) for 5 straight minutes before Rob aborted it. Two `py-spy` captures ~4 minutes apart, both identical, "active+gil" (single-threaded, genuinely blocked, not making progress): `EngineCore`'s main thread frozen inside `torch.cuda._lazy_init()`, reached via `Scheduler.__init__()` → `supports_multimodal_inputs()` → resolving the MiniMax-M3 model class → importing `vllm/models/minimax_m3/nvidia/model.py` → `fused_allreduce_gemma_rms_norm.py` → `vllm/compilation/passes/fusion/allreduce_rms_fusion.py`, whose module-level `import flashinfer.comm` triggers flashinfer's own eager `torch.cuda.get_device_capability()` probe (`flashinfer/jit/env.py`) — in `EngineCore`'s own process, which had never previously touched CUDA (all 4 Worker processes were confirmed genuinely idle and healthy, correctly waiting on their shm-broadcast queue — this is not the GLM-5.2 cross-rank NCCL desync pattern below, no GPU/network involvement at all). Nothing in ivllm's instrumentation catches this class of hang: it happens inside `EngineCore.__init__`, before vLLM's HTTP server or `/health` endpoint exist, so the startup loop just logs "waiting for vLLM /health" indefinitely — there's no overall startup wall-clock timeout independent of health-check success, and the idle-timeout/heartbeat mechanism only arms once status reaches `running`.

  **Why `IVLLM_DISABLE_FLASHINFER=1` (set in this job's yaml) didn't prevent it**: that flag (`disable-flashinfer-env.v0.25.1.v1.patch`, see `design/prototype/patch/README.md`) is a runtime early-return inside `_can_use_flashinfer()` — it stops the fused kernel from being *used*, but does nothing about `import flashinfer` itself, which two vLLM modules do unconditionally at module level, guarded only by `try/except ImportError` (which doesn't help — flashinfer *is* installed, it just hangs instead of raising): `vllm/compilation/passes/fusion/allreduce_rms_fusion.py` and `vllm/distributed/device_communicators/flashinfer_all_reduce.py`. Both get pulled in transitively the moment any code imports a model file that imports `fused_allreduce_gemma_rms_norm.py` (MiniMax-M3, GLM-5.2), independent of whether the fused kernel is ever called.

  **Fix v1 tested live — cleared the hang, but exposed a design flaw.** `disable-flashinfer-import.v0.26.0.v1.patch` (same `IVLLM_DISABLE_FLASHINFER` guard around both import sites) was applied to the real venv: `logs/mmax3q/20260903_161157/` confirms the hang is gone, ran to serving. But the API returned syntactically-valid, completely incoherent output (degenerate repeated-token loops — `Modifier Modifier Modifier...`, `t t t t...`, `ayayaya...`). No crash, no NaN/error, ~35-45s of sustained 100% GPU util per request — a real generation, just numerically wrong. Rob then tested removing `IVLLM_DISABLE_FLASHINFER` (since this job is single-node, TP=4 — `knowledge-base.md` scopes that flag to *multinode* only) to see if the fallback path was the culprit: **the `EngineCore` import hang came straight back**, confirmed. This is exactly what v1's design predicts — v1 ties "does `EngineCore` even attempt the import" to the *same* flag that governs "do Workers use the fused kernel," so there was no way to get both "no hang" and "Workers use the real flashinfer path" at once.

  **Root design fix, v2, drafted 2026-09-03**: Rob's framing — *"if we enable flashinfer we need to be explicit about which path it should take"* — decouple the two questions. `disable-flashinfer-import.v0.26.0.v2.patch` adds a second, independent guard: detect `EngineCore`'s own process via `setproctitle.getproctitle()` (vLLM itself sets this — `"VLLM::EngineCore"` / `"VLLM::Worker_TP0_EP0"` — confirmed by the exact strings `py-spy` captured while diagnosing the original hang, so this is an observed signal, not a guess) and **always** skip the import there, unconditionally — `EngineCore` never calls anything else in either patched file (every use of `flashinfer_comm` in `allreduce_rms_fusion.py` is inside a function body or behind `if flashinfer_comm is not None:`, so this is provably dead weight in that process). Workers keep importing flashinfer normally, gated only by `IVLLM_DISABLE_FLASHINFER` as originally intended. Verified to apply cleanly (`git apply --check`) against `vendor/vllm-0.26.0`, and round-tripped (apply for real → confirm → `git apply -R` → confirm pristine again) since `vendor/` is gitignored and `git status` can't verify it directly. **Not yet applied to the real venv or tested live.**

  **Recommended next test**: apply `v2` in place of `v1`, and since this job is single-node, **remove `IVLLM_DISABLE_FLASHINFER` from the yaml entirely** (or set `VLLM_FLASHINFER_ALLREDUCE_BACKEND=trtllm` explicitly, matching `knowledge-base.md`'s documented node-local-safe backend, rather than relying on auto-detection) — this should both keep `EngineCore` from hanging (v2's unconditional guard) and let Workers use the real fused kernel (no longer forced onto the fallback), which would confirm or rule out the fallback-path-correctness hypothesis in one test. See `design/prototype/patch/README.md` for the full writeup, including a still-open note: the currently-deployed `disable-flashinfer-env` fix is confirmed live on the cluster (its `info_once` log line appears in every `mmax3q` run) but has no tracked `v0.26.0` diff in this repo, only a `v0.25.1` one — worth reconciling.

- **CUDA device-state capture on a live vLLM worker has a genuine catch-22: no combination of the two available mechanisms gets you a valid device-side (kernel/warp/register) snapshot from a process you still intend to keep running.** Found during the GLM-5.2 coredump-tooling work, 2026-09-01/02.

  - **`report_cuda()`'s live `cuda-gdb -p <pid>` attach never returns device-side info, on this platform, full stop.** Checked every `cuda-gdb-node*.log` produced across the entire GLM-5.2 investigation (dozens of runs, both nodes) for any sign `-ex "cuda thread apply all backtrace"` ever returned *anything* — a kernel listing, block/thread indices, even cuda-gdb's own "No CUDA kernels" fallback message. Zero matches, ever. Every invocation is independently confirmed `Killed` by its `timeout -s 9 10s` wrapper rather than exiting cleanly via its own `-ex quit`, and the CUDA driver's own `"CUDA coredump is not supported with late attach. Disabling coredump."` message fires synchronously, adjacent in the log, to `report_cuda`'s own attach — i.e. attaching a live debugger to an already-running CUDA context is itself what triggers that message and disables device debugging for the process, on this driver/platform combination. The plain host-side `thread apply all backtrace` (everything this investigation actually used) does work and return promptly; only the device-side half is dead.
  - **The alternative — a user-triggered `CUDA_COREDUMP_PIPE`/`CUDA_COREDUMP_FILE` dump — only produces a valid, readable coredump when the `skip_abort` flag is *not* set.** With `skip_abort` (the flag combination needed to avoid killing the process, so capture could in principle be used repeatedly for ongoing monitoring), dumps come back truncated: `readelf -h` shows a "start of section headers" offset tens of gigabytes past the actual (~2GB) file size — confirmed on multiple independent dumps from the same run, all with the identical shape. This matches vLLM's own documented warning (`2025-08-11-cuda-debugging.md`) that `skip_abort` "has a documented bug that may cause illegal memory access errors on the GPU to be ignored," and is consistent with `skip_abort` letting the GPU context keep mutating state while the (large, non-memory-skipped) dump writer is still working, racing itself. Dropping `skip_abort` produces a valid, readable dump — but its side effect is that it **aborts the parent process** once the dump completes, so it can only ever be a one-shot terminal capture, never a repeatable observability mechanism you can fire against a still-being-monitored server.

  **Net effect**: today, getting a real device-side snapshot of a hung vLLM worker requires deliberately sacrificing that worker (`CUDA_COREDUMP_GENERATION_FLAGS` without `skip_abort`) — there is no way to capture one non-destructively for a process you want to keep serving from afterward. Not yet investigated: whether any other flag (rather than dropping `skip_abort` entirely) avoids the truncation while still avoiding the abort, or whether this is a hard tradeoff built into the mechanism on this CUDA/driver version.

- **vLLM's `--config <file>.yaml` loader silently drops boolean `false` values, defeating any flag whose real default isn't `False`** (upstream vLLM bug, `vllm/utils/argparse_utils.py`, confirmed against v0.25.1 via `vendor/vllm`). The yaml→argv conversion does:
  ```python
  if isinstance(value, bool):
      if value:
          processed_args.append("--" + key)
      # else: nothing appended — False is silently dropped
  ```
  This assumes every boolean flag's off-state is "flag absent," which is only true for flags whose CLI default is already `False`. For tri-state fields (`bool | None = None`, resolved later by other defaulting logic) omitting the flag does **not** mean off — it means "let some other default win," and that default is frequently `True`.

  **Confirmed affected, found during the MiniMax-M3 investigation (2026-08-07):**
  1. `enable-flashinfer-autotune: false` — `KernelConfig.enable_flashinfer_autotune` defaults to `None`, later filled in by the active `--optimization-level` preset (default **O2** → `True`; only `O0`'s preset defaults it to `False`). Every `vllm.yaml` in this repo that set `enable-flashinfer-autotune: false` had it silently ignored — flashinfer's autotune warmup dummy-run kept running every time, and was the actual root cause of a reproducible startup OOM chased across many separate MiniMax-M3 debugging sessions before this was traced. Since ivllm passes yaml straight through via `vllm serve --config vllm.yaml.clean.yaml`, every job in this repo relying on a bare `false` for this flag has been affected without any error or warning.
  2. `disable-hybrid-kv-cache-manager: false` — `SchedulerConfig.disable_hybrid_kv_cache_manager` has the identical `bool | None = None` shape, resolved later by several auto-disable heuristics in `VllmConfig` (platform support, chunked-local-attention+eagle, KV connector HMA support). Found in a DeepSeek config; didn't change observed behaviour in that case only because the heuristics happened to resolve to the same value anyway — same underlying defect.

  **Workaround** (proven working — already how `compilation-config`'s `fuse_allreduce_rms: false` correctly takes effect): wrap the field in its corresponding JSON-blob CLI arg instead of a bare top-level yaml key, e.g. `kernel-config: '{"enable_flashinfer_autotune": false}'` instead of `enable-flashinfer-autotune: false`. Dict-valued yaml keys are JSON-serialized as-is by the same loader and don't hit this code path.
  `no-enable-flashinfer_autotune: true` pattern is also an alternative.

  **Status**: reported upstream to `vllm-project/vllm`. Any `vllm.yaml` in `examples/` using a bare `key: false` for a flag whose default isn't already `False` should be audited and switched to the `*-config` JSON-blob form. This is fixed upstream but not sure what release it will be in.

- **SLURM (platform-level, not an ivllm bug): any job requesting more than 2 nodes in the "interactive" partition/reservation reliably gets step creation stuck on the 3rd node onward.** First seen via real `glm52`/`glm52q` jobs (job step creation for nodes 3/4 stuck indefinitely on `srun: Job step creation temporarily disabled, retrying (Requested nodes are busy)`, while nodes 1-2 come up fine every time), 2026-08-08 onward. Confirmed not specific to 4-node jobs — applies to any job over 2 nodes; "4-node" is just the case most tested since that's this partition's documented max.

  **Ruled out, in order**: wall-time/node-hours misunderstanding (`--time` is plain wall-clock, not multiplied by node count); `--exclusive` not being honoured (job-level allocation genuinely succeeds on all requested nodes every time — confirmed via `AllocMem`/`RealMemory` matching on the stuck nodes too, so the *allocation* is fine, only *step creation* on top of it fails); a client-side launch race in ivllm's own worker-loop (tested a `sleep 2` stagger between per-node `srun --overlap` calls — no difference); one specific broken physical machine (the identical positional pattern — always the 3rd/4th node, never the 1st/2nd — recurred across multiple, entirely different physical node sets, ruling out hardware); the QOS "2 total jobs" cap an Isambard admin (ticket #372791, "Anna") initially suspected (re-tested with a confirmed single job in the reservation via `squeue --all`, issue persisted); and, most recently, the `--cpus-per-task=72` CPU-allocation bug found during the GLM-5.2-INT4 investigation (see the `Mitigated` entry below — fixing it does not change this issue at all, confirmed by direct retest).

  **Real, separate finding along the way, not the root cause but worth keeping**: Isambard's "interactive" partition/reservation is configured `Hidden=YES`, so a plain `squeue --me` silently omits jobs running there entirely — `squeue --all` (or `--partition=interactive --reservation=interactive`) is required to see them at all. This cost real debugging time before being identified; `design/prototype/diagnose-stuck-nodes.sh` (built to automate diagnosis of this issue) accounts for it.

- **JIT cache growing without converging — RESOLVED, 2026-09-03.** `resolve_job_jit_cache()`'s "trust each subsystem's own content-addressed caching, don't key by node" design turned out to be sound in principle; two separate node-identity leaks were breaking it in practice, both now fixed (see below). Originally noticed during the GLM-5.2-INT4 investigation (`logs/glm52q/`): the shared JIT cache tarball reached ~7GB uncompressed (~900MB compressed) before being manually deleted, 2026-08-11 — described by the person debugging it as "quite unusual" growth, not the mild/expected kind.

  **Design context**: `resolve_job_jit_cache()`'s hash (model/TP/DP/PP/EP/vLLM-version only, deliberately excluding physical node/hostname identity — see the `Mitigated` entry below for the full reasoning) assumed this was safe because Triton/Inductor/DeepGEMM/flashinfer all do their own internal content-addressed caching, so different nodes landing in the same shared bucket would just additively coexist without correctness risk, converging toward a stable size once every genuinely distinct kernel variant had been seen. Sustained, non-converging growth run after run — for what should mostly be the same model/config — is inconsistent with that assumption holding.

  **Leading hypothesis**: `torch.compile`'s own on-disk cache path may bake in something machine-specific (e.g. exact GPU device identifier, not just architecture/compute-capability) rather than being purely content-keyed. With this reservation's ~1300-node pool, a long investigation session essentially never reuses the same physical hardware twice — so every run would add one node's worth of "new" entries for what might be identical kernel content, with no convergence ever possible. Directly observed (different investigation, `20260811_101945/`) that two different ranks got different `torch_compile_cache/<hash>/rank_N_0/` subdirectory names on two different nodes — consistent with, though not yet decisive proof of, this theory (the two data points were different ranks, not the same rank on two different nodes).

  **New correlation worth tracking**: `VLLM_USE_AOT_COMPILE=1` was absent from every one of the 21 `glm52q` runs before `logs/glm52q/20260811_154046/`, and present in every one of the 6 runs since (`154046`, `161429`, `164159`, `171124`, `172729`, `222935`) — exactly the window in which the growth was flagged as unusual. AOT compilation serializes a complete compiled artifact per rank (`saved AOT compiled function to .../torch_aot_compile/<hash>/rank_0_0/model`, already visible in earlier logs), plausibly much larger per-entry than incremental Inductor FX-graph-cache metadata — so if the per-node non-convergence theory above is right, `VLLM_USE_AOT_COMPILE` could be substantially amplifying the size of each new node's "wasted" contribution rather than causing the non-convergence itself. Not yet isolated from the node-identity variable.

  **Not yet done**: the decisive check would be comparing the `torch_compile_cache/<hash>/rank_0_0/` hash for the *same rank* across two runs confirmed to have landed on two *different* physical nodes, same model/config/AOT-compile setting otherwise — same hash both times rules out node-identity baking; different hash confirms it directly.

  **Practical mitigation applied, not a fix**: cache manually deleted 2026-08-11. Given how many one-off configs this investigation cycles through (and potentially now how many distinct physical nodes too), the cache is plausibly providing little real reuse benefit at this stage while adding real save/restore overhead every run — periodic manual deletion is reasonable for the duration of active investigation. Revisiting the cache-key granularity itself (e.g. whether `torch.compile`'s cache specifically needs node-scoping that the rest of the JIT cache doesn't) is lower priority than the main GLM-5.2 hang above and not yet started.

  **Root cause confirmed, 2026-09-03: the "leading hypothesis" above was right, and the specific mechanism is now known.** `$VLLM_CACHE_ROOT/torch_compile_cache` and its `torch_aot_compile` subdirectory each write a `cache-key-factors.json` per run-specific subdirectory, and that key is computed from (among other things) `VLLM_XLA_CACHE_PATH` — which `set_jit_caches()` sets to a **node-local** path (e.g. `/local/user/<uid>/<hostname>/<job>/xla`). Since that path embeds the hostname, every physical node this job lands on produces a different `torch_compile_cache` hash for otherwise-identical compiled artifacts, exactly the non-converging-growth pattern described above — this wasn't a `torch.compile`-internal machine fingerprint as originally suspected, it was ivllm's own node-local `XLA_CACHE_PATH` value leaking into a cache key that has nothing to do with XLA (GLM-5.2/this project's models don't use XLA at all — the variable being read into the hash appears to be a generic catch-all "path-like env vars" fingerprint on vLLM's side, not something specifically about XLA usage).

  **First fix applied**: removed `VLLM_XLA_CACHE_PATH` from `set_jit_caches()` (`src/engine/lib/utils.sh`) entirely, since nothing in this project's model set uses it and its only observed effect was poisoning this cache key with node identity.

  **Second, deeper cause found and fixed, 2026-09-03**: removing `VLLM_XLA_CACHE_PATH` stopped the cache *key* from varying by node, but a separate problem remained one level down — vLLM's own `InductorStandaloneAdaptor.initialize_cache()` (`vendor/vllm-0.26.0/vllm/compilation/compiler_interface.py:463-480`) bakes the node-local scratch path itself into the compiled artifacts it writes under `torch_compile_cache/<hash>/rank_i_j/inductor_cache` (it explicitly tracks `compiled_fn.__code__.co_filename` and expects it to start with the cache dir's own absolute path). Since `resolve_localdir()` built that path as `/local/user/<uid>/$(hostname -s)/<job>` (`utils.sh:111`, now superseded), every node produced artifacts baked with a different, node-specific absolute path — non-portable even once the cache *key* itself converged, breaking restores of a cache tarball saved on one node onto a different node (or even the same node on a later job with a different job name). **Fix**: dropped the hostname component from `resolve_localdir()` entirely — `node_local="$LOCALDIR/$job"` instead of `"$LOCALDIR/$(hostname -s)/$job"` (`utils.sh:111-117`). Safe because `/local` is genuinely a per-node RAM-tmpfs mount (never shared across nodes), so the hostname was never providing real isolation — `$LOCALDIR` (`/local/user/<uid>`) already scopes by user, and `$job` already scopes by job; two nodes never see each other's copy of this path regardless of what string it contains. This makes every node produce the *identical* absolute local-scratch path for a given job, so paths baked into `torch_compile_cache` (and anything else that does the same thing) stay valid no matter which node restores the cache. **Confirmed working by Rob, 2026-09-03: verified across 2 runs on qwen38.**

- **Nemotron-3-Ultra-550B multinode (Ray, TP=8 across 2 nodes) hung reliably within minutes of every real run, 2026-08-04/05.** Every attempt (dozens, across the `multinode ray support` work) died the same way: `vLLM` served startup/warmup and a handful of real requests fine, then `EngineCore` logged `"No available shared memory broadcast block found in 60 seconds"` five times (~300s) before `TimeoutError: RPC call to sample_tokens timed out` → `EngineDeadError`.

  **Investigation path** (see conversation history for full detail; summarised here for anyone picking this back up):
  1.   2.   3. A real hung run captured with this instrumentation showed something different from the Triton-JIT theory: **all 8 worker ranks, both nodes, frozen at the identical frame** — `torch.cuda.graphs.CUDAGraph.replay()`, inside the MTP (`nemotron_h_mtp`) draft model's forward pass (`propose_draft_token_ids`) — no compilation involved, JIT had finished minutes earlier. The GPU-utilisation snapshot was the deciding evidence: 7 of 8 GPUs pegged at 100% (consistent with legitimately spinning inside a stuck NCCL collective) but **rank TP0/EP0 on the head node sat at 0%** the entire ~4-minute hang — everyone else waiting on it, it doing nothing.
  4. This matches [vLLM issue #46097](https://github.com/vllm-project/vllm/issues/46097) almost exactly: a multi-node TP CUDA-graph-replay NCCL collective deadlock, independently reported on a different model, diagnosed there as "the ranks are likely not in the same collective instance" — a tensor-parallel control-flow divergence, not a compile-timing issue. That thread's own discussion (read via the GitHub API, since `gh` isn't authenticated in this environment and the GitHub web UI doesn't render comments through `WebFetch`) found the divergence to be **NCCL-build-specific, not version-specific**: two builds of the identical version string (`2.28.9`) — a `pip` wheel vs. the OS vendor's `apt` package — behaved completely differently (deadlock vs. stable), identifiable only by SHA256/Build ID, not by version string, log banner, or `NCCL_VERSION` env var (all shown to be unreliable/stale in that thread).
  5. Built `design/prototype/nccl-probe.sh` (non-invasive, read-only) to check Isambard's actual situation: confirmed **torch/vLLM's default NCCL is the bundled `nvidia-nccl-cu12` pip wheel (2.28.9)**, not NVHPC 26.3's bundled copy (2.29.3) or anything from the `brics/nccl` module (which turned out to provide no `libnccl.so` at all — likely just the `aws-ofi-nccl` plugin). Confirmed via direct `ncclGetVersion()` ctypes calls (not `torch.cuda.nccl.version()`, which turned out to be **misleading in practice** — it kept reporting the old version even after the on-disk file was replaced and reloaded, implying it's a value baked into the torch wheel at torch's own build time, not a live query). Also confirmed `LD_PRELOAD`-ing an alternative NCCL does **not** override torch's own bundled copy — torch loads its own file by absolute path regardless, so both end up mapped and torch's own copy is what's actually used.

- **GLM-5.2-AWQ-INT4 (TP=8×EP across 2×4-GPU nodes) hangs with the same "one rank stuck, rest spinning" signature as the Nemotron and MiniMax-M3 investigations above** (`logs/glm52q/`, 2026-08-10/11). Every attempt: real serving proceeds fine for a while, then `EngineCore` logs `"No available shared memory broadcast block found in 60 seconds"` repeatedly with no recovery, requiring a manual `ivllm cancel` (exit 254, "user abort"). Same class of hang as Nemotron's, on a third, unrelated model and a third quantization scheme (AWQ INT4). Extensively tuned; a real, independently-useful bug was found and fixed along the way (the CPU allocation issue below), but the core hang itself remains unresolved — **paused as of 2026-08-11**, this entry covers what's actually moved the needle vs what hasn't, so it doesn't need re-litigating from scratch.

  **Diagnosis (mechanism, consistent across every variant tried)**: `IVLLM_DEBUG_LEVEL: 3`'s pyspy traces plus periodic `report_memory()` GPU snapshots always show the same terminal shape: `EngineCore` blocked in `shm_broadcast`'s `dequeue`/`get_response`, waiting for a worker response that never arrives; N-1 of the 8 workers have already finished their step and are parked in a device-sync (`_bookkeeping_sync → _to_list` in `sample_tokens`, which forces a CUDA stream sync); exactly one worker is caught either (a) already back in its idle busy-loop having apparently exited a collective early with no exception logged (the async-scheduling variant, `step_with_batch_queue`), or (b) genuinely still inside a live collective, e.g. `ncclAllGather` in `compute_logits` (the no-async-scheduling variant, plain `step()`). Matches the TP-rank control-flow divergence class documented in vLLM issue #46097 (cited in the Nemotron entry above) and in [vllm-project/vllm#43420](https://github.com/vllm-project/vllm/issues/43420) (`RayExecutorV2`'s `shm_broadcast` assumes single-host shared memory, closed upstream as architectural/not-planned — a close mechanism match, though that issue's own downstream symptom, a 30-minute Gloo-TCP timeout, has never actually been observed here since jobs get manually aborted first).

  **Changes that measurably helped (keep these as the baseline going forward)**:
  - **`no-async-scheduling: true`** — changes which failure mechanism you hit, not just cosmetically: with async scheduling (vLLM's default) the hang reproduces fast via the `step_with_batch_queue` variant above; with it off, the hang shifts to the "genuinely-still-computing straggler" variant and survival time before hanging goes from near-immediate to many minutes of real serving. Confirmed in both directions — re-enabling async (`logs/glm52q/20260811_095817/`, done by accident while testing something else) reliably reproduced the fast hang again.
  - **`NCCL_NET_GDR_LEVEL: PHB`** (vs the default `SYS`) — cleanest isolated comparison available: `logs/glm52q/20260811_104623/` (PHB) sustained ~8m19s of real serving before hanging vs `logs/glm52q/20260811_092257/` (SYS, otherwise identical config) at ~2m49s — roughly 3x. Doesn't prevent the hang, delays it. Consistent with `PHB`'s stricter GPUDirect-RDMA eligibility check pushing whichever rank has flaky topology detection (see below) off a fast-but-unreliable path onto a slower, more conservative one.
  - **`--network=disable_rdzv_get`** (sbatch flag, added to pair with the pre-existing `FI_CXI_RDZV_PROTO=alt_read`) — per [HPE's Slingshot rendezvous-protocol docs](https://support.hpe.com/hpesc/public/docDisplay?docId=dp00005991en_us&page=user/rendezvous_protocol_configuration.html), `alt_read` requires this SLURM allocation flag to actually take effect; it had been missing from every prior run, meaning `alt_read` was silently half-applied the whole time. `logs/glm52q/20260811_104623/` (with this fix, on top of the PHB+no-async baseline) produced the single longest/most successful run yet — ~7.5 min of sustained serving, a dozen+ successful completions, survived a multi-minute mid-session idle gap that no prior config survived. The eventual hang, once it did occur, was byte-identical in signature to every other run. Real improvement, not a fix.

  **Changes tried that made no measurable difference**:
  - Worker-launch stagger (`sleep 2` between per-node `srun --overlap` calls) — ruled out a client-side launch race as the cause.
  - [uccl-project/uccl#956](https://github.com/uccl-project/uccl/issues/956)-inspired CXI tuning: `FI_CXI_RX_MATCH_MODE` (`software`→`hybrid`), `FI_CXI_DEFAULT_TX_SIZE` (`1024`→`2048`) — no change to the hang; if anything the run right after this change hung modestly *faster* (`logs/glm52q/20260810_215408/`, ~8m9s vs ~9m53s), though that's within plausible JIT-compile-time noise.
  - `FI_CXI_RDZV_THRESHOLD`/`RDZV_GET_MIN`/`RDZV_EAGER_SIZE=0` — turned out not to even fully apply: libfabric's own `cxip_env_init()` silently floors the threshold to 192 bytes regardless (visible once `FI_LOG_LEVEL=warn` was enabled).
  - Full revert of all `FI_CXI_*` overrides back to `vllm-env.sh`'s defaults (software match mode), keeping only `NCCL_NET_GDR_LEVEL: PHB` and `no-async-scheduling: true` — reported as making no difference to the underlying hang versus the PHB+no-async baseline.
  - **`numa-bind: true` — confirmed to never take effect, for two independent reasons found in sequence.** First, `resolve_stripped_job_config()` was silently deleting the `numa-bind` key before it ever reached `vllm serve` (since fixed). Second, even with that fixed and `numa-bind: true` confirmed present in `vllm.yaml.clean.yaml`, still zero `numactl`/`"Binding worker subprocess"` log output ever appeared (`logs/glm52q/20260811_121151/`) — traced to an upstream gap: `configure_subprocess()` (`vllm/utils/numa_utils.py`), the function that actually wraps a worker's launch in `numactl`, is only called from `v1/executor/multiproc_executor.py` and `v1/engine/utils.py` (the latter for `EngineCore` itself, regardless of executor backend). `v1/executor/ray_executor_v2.py` has zero references to it or to NUMA anywhere. Since this deployment requires `distributed-backend-executor: ray` for its multi-node topology, `numa-bind` cannot affect any of the 8 GPU worker processes here — confirmed structurally, not just by absent log lines. Drop it from future GLM-5.2 runs; it's dead weight for any Ray-executor deployment on this vLLM version (`0.26.0`).

  **Real bug found and fixed: `slurm-ray-vllm-serve.sh` was starving every node's Ray cluster of CPUs, and this fully explains the "usually slot 2" pattern below (now closed).** The two `srun --overlap` calls that launch `ray-setup.sh` (head start, worker start) requested `--cpus-per-task=72` — a *flat 72 CPUs for the entire node*, shared across all 4 GPU workers Ray spawns plus its own daemon overhead, versus the mp-path's `slurm-vllm-serve.sh` correctly using `--cpus-per-gpu=64` (256 total). This directly explained the recurring `ncclTopoGetCpuAffinity: Affinity for GPU N is empty, ignoring` warnings seen in every prior run: with only 72 of the node's ~288 real cores in the cgroup, NCCL's own topology auto-detection couldn't find a non-empty intersection between most GPUs' true NUMA-local range (e.g. `144-215` for GPU2) and the process's actual (uniformly `0-71`) affinity.   **Leading theory as of 2026-08-11, found by reading the actual vLLM source at the exact hang point rather than continuing to vary external config**: a real, independently-documented weak-memory-ordering bug class in `vllm/distributed/device_communicators/shm_broadcast.py` — the exact module every single hang in this entire investigation (Nemotron, MiniMax-M3, GLM-5.2) bottoms out in (`EngineCore`'s `dequeue`/`acquire_read`, workers' `enqueue`/`acquire_write`). This module implements a hand-rolled, lock-free cross-process synchronization scheme over raw shared-memory metadata bytes (no OS locks), whose correctness depends entirely on a custom `memory_fence()` being called at exactly the right points:
  ```python
  def memory_fence():
      # Implementation acquires and immediately releases a lock. Python's
      # threading.Lock provides sequentially consistent memory barrier semantics
      # across all major platforms (POSIX, Windows).
      with _memory_fence_lock:
          pass
  ```
  That documented assumption — an ordinary process-local `threading.Lock` providing sufficient cross-process, cross-core memory-barrier semantics — is safer on x86 (strong TSO ordering, where vLLM's development/CI is overwhelmingly hosted) than on **aarch64**, which is what every GH200 node's Grace CPU is.

  **This is not speculation from reading code in isolation — it's a confirmed, real, previously-reported bug class in this exact file, on this exact CPU architecture**, found via `git log` on `vendor/vllm` (full clone, all tags) plus a web search once the pattern was clear:
  - [`vllm-project/vllm#27858`](https://github.com/vllm-project/vllm/issues/27858) — filed independently by a real user, explicitly on **aarch64** (`Architecture: aarch64` in their environment report), describing this exact gap in their own words: *"Before `metadata_buffer[0] = 1` is set, we should make sure that `buf` is synchronized across processes."* Their symptom was sporadic pickle/deserialization corruption rather than a clean hang, but the same root mechanism — a reader observing the "ready" flag before the buffer contents are actually visible to it.
  - `PR #30407` ("fix(shm): Add memory barriers for cross-process shared memory visibility", Dec 2025) — introduced `memory_fence()` from scratch; almost certainly the direct response to `#27858`.
  - `PR #32022` ("[Bugfix] Fix memory inconsistency in cross-process shared memory", Feb 2026) — a **second**, separately-needed fence added just ~2 months later, at a spot the first fix missed, with its own commit comment explicitly citing "CPU architectures with weak ordering."
  - `PR #28053` ("[Core] Remove busy loop from idle buffer readers", March 2026) — a large (258-line) rewrite of the *entire waiting mechanism* immediately after both fence fixes, replacing a simpler busy-loop with the current ZMQ-notification-based `SpinCondition` class. This newer code was never specifically re-audited for the same class of issue the two fence PRs were written and tested against. **Correction, found via `VLLM_USE_SPINLOOP_EXT` research**: #28053 only removed the *idle* busy-spin — [PR #36517](https://github.com/vllm-project/vllm/pull/36517) ("Efficient Busy Polling Optimization") confirms, via a direct maintainer exchange, that **a busy-poll path still exists under load** in the current code (the PR author verified `monitorx`/`mwaitx` power savings "under load," which only makes sense if busy-polling is still happening then). So the notification-vs-busy-poll picture is more nuanced than "idle readers now sleep, done" — there's still a busy-poll code path active under some conditions, worth understanding before assuming the ZMQ-notify rewrite fully replaced spinning everywhere.

  Both fence fixes are present in our installed `0.26.0`, confirmed by direct read of the vendored source — so the *already-known, already-reported* bug is fixed. But the vLLM team needing two separate passes to get the fencing right on their first, simpler implementation, followed by a substantial rewrite of the surrounding logic that was never re-audited for the same issue, makes a third, still-undiscovered gap in the newer notification path entirely plausible — and this is the first explanation across the whole investigation that would account for *why* nothing at the NCCL or libfabric level has ever shown an anomaly during a live hang: the bug wouldn't be in the network or GPU collective path at all, it'd be in this host-CPU shared-memory IPC mechanism between `EngineCore` and its workers, which every diagnostic tried so far (pyspy, NCCL logs, libfabric traces) has been looking *around*, not *at*.

  **Patchable, pure Python, no recompilation needed** (`vllm/distributed/device_communicators/shm_broadcast.py`) — same `apply-vllm-patch.sh` mechanism already used for `hybrid-trtllm.sh`/`disable-flashinfer-env.v0.25.1.patch` applies directly. **Decided to bottom this out further before reporting upstream, rather than filing on the strength of the code-reading + precedent alone.** Concrete next steps for whoever picks this back up:
  - Read `PR #28053`'s full diff and its own `test_shm_broadcast.py` additions closely — check whether the new `SpinCondition`/ZMQ-notify path has its own explicit "subscriber ready" handshake analogous to the data-channel's `wait_until_ready()`, or whether there's a ZMQ PUB/SUB "slow joiner" race (a message sent before a SUB socket's background connection handshake completes is silently dropped) — this would be a *second*, independent bug in the same file, distinct from the memory-fence question, also worth ruling in or out.
  - Try strengthening `memory_fence()` beyond the `threading.Lock` implementation — e.g. an explicit hardware barrier via a small `ctypes` call to `__sync_synchronize`/a compiler atomic-fence built-in — and see if hang frequency/timing changes at all. A change either way is informative.
  - If any x86 GPU hardware is available anywhere (even outside Isambard), check whether the identical config reproduces the hang there at all, or takes measurably longer to. Strong x86 TSO ordering could plausibly mask this class of race almost entirely, making a clean x86/aarch64 comparison close to differential proof.
  - Once reasonably confident, file upstream referencing `#27858`/`#30407`/`#32022`/`#28053` directly and our own symptom (GH200/aarch64, multi-node Ray executor, response never arriving) — this is a core, widely-shared vLLM mechanism, not something specific to this deployment, so a confirmed residual gap would be valuable well beyond this project.

  **Confirmed via `git fetch --tags` on `vendor/vllm` (2026-08-11): the file has been touched again since `0.26.0`, and two of the four commits between `0.26.0` and the now-available `0.27.1` look like an extremely strong match, independent of the memory-fence theory above.**
  - [`10c75477b`](https://github.com/vllm-project/vllm/commit/10c75477b) — "shm_broadcast: bound idle reader waits and release read slots" (#45224, July 2026). Two fixes in one: (a) previously, an idle reader waiting indefinitely with no active warning/deadline could get a `None` poll timeout on the ZMQ notify socket — an infinite wait with **zero periodic fallback recheck** of the actual SHM flag. If that one notification is ever lost (a real risk in the ZMQ-`SpinCondition` mechanism `#28053` introduced), the reader hangs forever even though the data was already correctly written. Fixed by capping every wait at a new `SHM_READER_RECHECK_INTERVAL_MS = 5000` unconditionally. (b) the read-completion flag was previously set *after* `yield buf` with nothing guaranteeing it ran if the caller raised mid-processing — wrapped in `try`/`finally`. This second half directly matches the abort/cancellation observation noted above: an exception while handling a cancelled request's response could permanently strand a reader's slot as "not read," leaving the writer waiting forever for a completion that could structurally never happen.
  - [`48aa8d8d7`](https://github.com/vllm-project/vllm/commit/48aa8d8d7) — "Prevent stale multiproc RPC deadlines from becoming unbounded waits" (#41357, July 2026). A sign bug: `deadline - time.monotonic()` going slightly negative (any small scheduling delay past an intended deadline) produced a negative timeout passed to `zmq.Socket.poll()`, which treats negative timeouts as *block indefinitely* (`-1` is libzmq's own convention) rather than *already expired*. Fixed via `max(0, ...)` clamping in both `shm_broadcast.py` and `multiproc_executor.py`.
  - The other two commits in this range (`831d3848f`, fail-fast on undersized `/dev/shm`; `a07fac758`, zero-copy tensor pickling perf) are unrelated to hangs specifically.

  **Lead from libfabric's own manual, investigated and closed: a documented "CUDA deadlock" mechanism exists, but GDRCopy was the wrong tree for CXI specifically.** Per `fi_endpoint(3)`/the libfabric manual: `cudaMemcpy()` calls made *inside libfabric itself* can deadlock when a CUDA kernel blocks waiting on a host-side `cudaMemcpy` to complete — a real, named failure mode, not this project's own speculation. Two documented mitigations exist: (1) GDRCopy (`NCCL_GDRCOPY_ENABLE`/`FI_HMEM_CUDA_USE_GDRCOPY`); (2) `FI_OPT_CUDA_API_PERMITTED=false`, an `fi_setopt(FI_OPT_ENDPOINT, ...)` call restricting an endpoint from making CUDA API calls at all — **not usable from ivllm today**, since it's an application-code API call, not an environment variable, and it isn't confirmed whether `aws-ofi-nccl` (the actual libfabric caller in this stack) exposes an equivalent env-settable knob. GLM-5.2's longest-surviving run happened to flip `NCCL_GDRCOPY_ENABLE`/`FI_HMEM_CUDA_USE_GDRCOPY` to `1` alongside the `PHB` change (not isolated from that test, so still unconfirmed either way) — three follow-up findings now rule this out entirely rather than just downgrade it: (a) per `fi_cxi(7)` (`design/references/fi_cxi.md`, confirmed direct quote): *"the CXI provider enables ... FI_HMEM_CUDA_USE_DMABUF by default if not specifically set"* — DMABUF is a different zero-copy mechanism that also avoids a host-side `cudaMemcpy` in the transfer path, so CXI already sidesteps this deadlock class by default, without GDRCopy, and `fi_cxi(7)` never mentions GDRCopy at all; (b) per `nccl.md` (`design/references/nccl.md`): `NCCL_DMABUF_ENABLE` defaults to `1` (enabled) at the NCCL layer too, independent of CXI — a second, separate default pointing at DMABUF; (c) `NCCL_GDRCOPY_ENABLE` itself does not appear anywhere in that same 102-variable NCCL reference, a real question mark over whether it does anything at all in whatever NCCL build ivllm runs. Separately, there's a real, maintainer-confirmed, CXI-specific race condition in the GDRCopy cleanup path — [ofiwg/libfabric#10041](https://github.com/ofiwg/libfabric/issues/10041), a double-free when two threads unmap/unpin the same GDR handle, reported on multi-node Slingshot 11 (this project's exact fabric), maintainer quote: *"very much tied to the cxi provider"* — looks stale (last real human activity Aug 2024) rather than deliberately ruled out, no workaround documented. Net: every layer of this stack already defaults to DMABUF without needing GDRCopy; explicitly enabling GDRCopy adds a live, unresolved crash risk with no confirmed benefit. **Closed — not a fix candidate.** See `knowledge-base.md`'s Mandatory table for the full sourcing.

  **Live run, 2026-08-12, `logs/glm52q/20260812_213446/`: `disable-custom-all-reduce: true` tested — does NOT fix the hang, but this run's diagnostics finally pinpoint the exact freeze location, and it reframes the whole investigation.** Same signature as ever operationally (exit 254, user abort after ~13 min, `[ivllm-diag]` shows `queue=response[rank=0]` stuck, first at `written_flag=0/own_read_flag=0` during a transient warmup-time stall that resolved, then permanently from ~21:31:20 with `written_flag=1/own_read_flag=1` — the "already fully consumed, EngineCore correctly waiting for the next response" state, not a lost-notification bug). **#8410's custom-all-reduce hang mechanism is now ruled out for this specific hang** — disabling it changed nothing.

  **The new, decisive evidence is in the pyspy dumps.** At 21:31:24 (just as the hang locks in) and again at 21:32:17, 21:33:something, and 21:34:13 (unchanged, over 3 minutes later — a genuine freeze, not a coincidentally-sampled fast path), **all 8 GPU workers, both nodes, are frozen at the identical Python frame**:
  ```
  _to_list (vllm/v1/worker/gpu_model_runner.py:7769)
  _bookkeeping_sync (vllm/v1/worker/gpu_model_runner.py:3727)
  sample_tokens (vllm/v1/worker/gpu_model_runner.py:4669)
  ```
  Read directly from `vendor/vllm-0.26.0`: line 7769 is `self.transfer_event.synchronize()` inside `_to_list()` — a `torch.Event()` recorded on the current (default) CUDA stream right after a non-blocking pinned D2H copy of the sampled tokens. The function's own comment explains why it exists: *"`tolist` would trigger a cuda wide stream sync, which would block other copy ops from other cuda streams... A cuda event sync would avoid such a situation"* — citing [vllm-project/vllm#22754](https://github.com/vllm-project/vllm/issues/22754) as the original motivating issue. Per `_bookkeeping_sync`'s own comment a few lines up: this event "waits for every D2H queued on the default stream since the last sync" — i.e. `transfer_event.synchronize()` blocks the Python thread until **everything else already queued on that rank's default CUDA stream this iteration has finished**, including every attention/MoE/allreduce kernel issued earlier in the same forward pass. Fetched #22754 directly: it documents the original stream-blocking problem and the event-based fix, but **contains no discussion of whether the event-based fix can itself hang** — this specific failure mode looks genuinely unreported upstream.

  **This reframes the entire investigation.** `shm_broadcast.py` (memory fences, `SpinCondition`, lost notifications — all the prior theories) is not where the bug lives — it's just the mechanism by which EngineCore *reports* that a worker never sent a response. The worker never gets that far because it's frozen **inside its own forward pass**, at a point that only blocks if an *earlier* kernel on that same GPU's default stream never completes. Since all 8 ranks show the identical frozen state simultaneously (not staggered, not diverging), the most coherent explanation is a genuine cross-rank NCCL/collective desync somewhere in the forward pass (TP allreduce or MoE/EP dispatch-combine) — some rank never receiving or sending its side of a collective — which stream-orders into every rank's own `_to_list()` call hanging behind it. This is the second confirmed occurrence of this *exact* frame (also seen in `20260811_233628`, both times localized to node0/`queue=response[rank=0]`) — a real, reproducible, precise signature, not a one-off.

  **This directly validates and reprioritizes the `TORCH_NCCL_DESYNC_DEBUG`/flight-recorder recommendation above** — that diagnostic exists specifically to answer "which rank/collective is desynced," which is now clearly the right question to be asking, more so than continuing to audit `shm_broadcast.py`'s IPC layer. It should be the next thing tried, not one item among several.

  **Verified: NCCL's own verbose logging (`NCCL_DEBUG=INFO`) is exhausted as a diagnostic avenue here too, for the same reason as libfabric's.** Checked every rank's last logged NCCL line in this run: all 8 (both nodes) logged an `AllReduce`/`AllGather` launch in the same narrow window right before the freeze (~21:31:10–21:31:20) — consistent with the pyspy evidence that every rank was still mid-forward-pass at that point — then **zero further NCCL log lines from any rank for the entire ~3.5-minute hang** (out of 9825 total NCCL log lines in the run). `NCCL_DEBUG=INFO` only logs at collective *launch*, not while a rank is blocked waiting inside one — so once something stalls mid-collective there's structurally nothing further to log. Confirmed exhausted, not worth turning up further (proven, this run).

  **Important gotcha found for the `TORCH_NCCL_DESYNC_DEBUG`/flight-recorder plan above: it likely wouldn't have fired yet in any run so far.** vLLM's own default `--distributed-timeout-seconds` (the `torch.distributed.init_process_group` timeout for NCCL groups) is **600 seconds** (per `vllm-serve-cli.md`). `TORCH_NCCL_DESYNC_DEBUG`/the flight recorder's dump-on-timeout mechanism only activate when PyTorch's own NCCL watchdog detects a timed-out collective — i.e. only after that full 600s window elapses. This run's confirmed hang window (last successful activity ~21:31:20 to the manual abort at 21:34:45) was only ~3.5 minutes/~210s — well short of 600s. **Every hang so far has likely been manually cancelled before the watchdog ever got a chance to fire**, meaning `TORCH_NCCL_DESYNC_DEBUG=1` alone, set the same way every other env var has been, would produce nothing regardless of whether it's "working." For the next run: (1) set the full diagnostic set together — `TORCH_NCCL_DESYNC_DEBUG=1`, `TORCH_NCCL_TRACE_BUFFER_SIZE=2000` (must be `>0` for anything to populate), `TORCH_NCCL_DUMP_ON_TIMEOUT=1`, `TORCH_NCCL_TRACE_CPP_STACK=1` — `DESYNC_DEBUG` alone won't populate the flight recorder without the trace buffer being sized; (2) also set `TORCH_NCCL_DEBUG_INFO_PIPE_FILE=<job debug dir>/torch_nccl_dump_trigger` so a dump can be **manually forced** the moment the existing fast (~60s) `"No available shared memory broadcast block"` warning appears, by writing anything to that pipe — this sidesteps the 600s wait entirely; (3) if manual triggering proves awkward, fall back to patience — let the job sit stuck for at least ~11 minutes past the point it looks hung before running `ivllm cancel`, so the automatic on-timeout dump gets its full window (documentation for the default timeout; inferred for why prior attempts, if any, would have produced nothing).

## Resolved

- **`bun:test` cannot reliably exercise umask-dependent child-process behaviour** (testing-infrastructure finding, not a product bug — kept here for the record since it cost real investigation time and could recur). While building the `copyDirectory` permission tests above, a test asserting group-write via the `--rsync-path 'umask 002 && rsync'` mechanism *alone* (before the `chmod -R g+rwX` fix existed) consistently failed under `bun test` but passed when the identical code (same `SshRemoteOps` class, same fake-`ssh`-on-PATH fixture used in `tests/unit/SshRemoteOps.test.ts`, same `process.umask(0o022)` simulation) was run via plain `bun run` instead — and the `bun run` result matched real Isambard behaviour. Conclusion: Bun's test runner (`1.3.14`) does something that breaks umask inheritance from a test's `process.umask()` call down to a spawned child process; the exact internal mechanism wasn't identified further. This is no longer blocking anything — the shipped fix (explicit `chmod -R g+rwX`) is deterministic and untroubled by this, so all three tests in `tests/unit/SshRemoteOps.test.ts` pass reliably under `bun:test`. Documented here in case a *future* test ever needs to depend on umask propagating to a spawned child under `bun test` — that will hit the same wall.
