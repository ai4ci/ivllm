# Active Issues

This document tracks known, pre-existing bugs in the `isambard-vllm` repository.

## Known Issues

- **`capture_job_diagnostics()` does not force copied files group-writable** (`src/engine/lib/utils.sh`). It copies failed-job artifacts via plain `cp -f` (`vllm*.log`, `vllm.yaml`, `status.json`) into the diagnostics directory, but never does a follow-up `chmod g+w` on the copied *files* — only the diagnostics directory itself gets the group-writable/setgid treatment (`2775`, correct). Like the historical `copyDirectory()` bug documented below, plain `cp` without `-p` still uses the *source* file's mode bits as its base request, so a source log file without group-write (e.g. `644`) stays `644` in the diagnostics copy instead of becoming `664`. Surfaced by `tests/bash/sandboxed/test-diagnostics.sh`'s `capture_job_diagnostics_forces_group_writable_even_from_restrictive_source`, which was previously failing on an *earlier* assertion (the directory mode, before the `775`→`2775` permissions overhaul) and never actually reached this one until that first assertion was fixed to match the new scheme.
  **Suggested fix:** add an explicit `chmod g+w` on each file after the `cp -f` calls in `capture_job_diagnostics()`.

- **`tidy_up()` reports the wrong reason string for a SLURM timeout** (`src/engine/lib/utils.sh:845`). The `SIGUSR1` handler — documented everywhere else as meaning "SLURM timeout" (see the comment at `utils.sh:929` and the trap setup at `utils.sh:939`) — calls `update_reason "$job" "SLURM job cancelled"` instead of `"SLURM timeout"`. Looks like a plain copy/paste of the cancel-path's reason string into the timeout path. Surfaced by `tests/bash/sandboxed/test-exit-trap.sh`'s `tidy_up_200_triggers_slurm_timeout`.
  **Suggested fix:** change the string literal at `utils.sh:845` to `"SLURM timeout"`.

- **vLLM's `--config <file>.yaml` loader silently drops boolean `false` values, defeating any flag whose real default isn't `False`** (upstream vLLM bug, `vllm/utils/argparse_utils.py`, confirmed against v0.25.1 via `vendor/vllm`). The yaml→argv conversion does:
  ```python
  if isinstance(value, bool):
      if value:
          processed_args.append("--" + key)
      # else: nothing appended — False is silently dropped
  ```
  This assumes every boolean flag's off-state is "flag absent," which is only true for flags whose CLI default is already `False`. For tri-state fields (`bool | None = None`, resolved later by other defaulting logic) omitting the flag does **not** mean off — it means "let some other default win," and that default is frequently `True`.

  **Confirmed affected, found during the MiniMax-M3 investigation (2026-08-07):**
  1. `enable-flashinfer-autotune: false` — `KernelConfig.enable_flashinfer_autotune` defaults to `None`, later filled in by the active `--optimization-level` preset (default **O2** → `True`; only `O0`'s preset defaults it to `False`). Every `vllm.yaml` in this repo that set `enable-flashinfer-autotune: false` had it silently ignored — flashinfer's autotune warmup dummy-run kept running every time, and was the actual root cause of a reproducible startup OOM chased across many separate MiniMax-M3 debugging sessions before this was traced. Since ivllm passes yaml straight through via `vllm serve --config vllm.yaml.clean.yaml`, every job in this repo relying on a bare `false` for this flag has been affected without any error or warning.
  2. `disable-hybrid-kv-cache-manager: false` — `SchedulerConfig.disable_hybrid_kv_cache_manager` has the identical `bool | None = None` shape, resolved later by several auto-disable heuristics in `VllmConfig` (platform support, chunked-local-attention+eagle, KV connector HMA support). Found in a DeepSeek config; didn't change observed behaviour in that case only because the heuristics happened to resolve to the same value anyway — same underlying defect.

  **Workaround** (proven working — already how `compilation-config`'s `fuse_allreduce_rms: false` correctly takes effect): wrap the field in its corresponding JSON-blob CLI arg instead of a bare top-level yaml key, e.g. `kernel-config: '{"enable_flashinfer_autotune": false}'` instead of `enable-flashinfer-autotune: false`. Dict-valued yaml keys are JSON-serialized as-is by the same loader and don't hit this code path.

  **Status**: reported upstream to `vllm-project/vllm`. Any `vllm.yaml` in `examples/` using a bare `key: false` for a flag whose default isn't already `False` should be audited and switched to the `*-config` JSON-blob form.

- **`ray-run-vllm.sh` references `$IVLLM_JOB` before the script ever sets it from `$1`** (`src/engine/lib/ray-run-vllm.sh`). The top of the script resolves `min-vllm-version` and env-exports via `get_job_config_setting "$IVLLM_JOB" ...` / `get_job_config_exports "$IVLLM_JOB"` — but `IVLLM_JOB=${1:?must set job name}` doesn't appear until several lines *later*, after `common-env.sh`/`vllm-env.sh` are sourced and the vLLM venv is activated. `IVLLM_JOB` is never `export`ed anywhere up the call chain (`ivllm-serve.sh` keeps it as a plain local variable; only `IVLLM_LOG` is exported), so at the point of those early reads it's whatever's ambiently unset/inherited — not the real job name passed as this script's own argument. Deterministic, not a race: every later line (`model`, `serverPort`, `strippedConfig`, all read *after* the correct `IVLLM_JOB=${1:?...}` assignment) gets the right job's data, so only version/env-export resolution is silently wrong. Surfaced as two different vLLM installs running within the same job (driver process on one version, Ray worker actors on another) once `min-vllm-version` was bumped for a versioned re-test — see the MiniMax-M3 entry below, step 12. Fix: hoist `IVLLM_JOB=${1:?must set job name}` to the top of the script, before anything references it.

- **JIT cache save/restore is job-name-keyed, not node-keyed, and restored unconditionally on every node** (`src/engine/lib/utils.sh`: `resolve_job_jit_cache()`, `save_cache()`, `restore_cache()`). The persistent cache tarball lives at `$HOME/.cache/ivllm/<job>/jit-cache.tar.gz` — no hostname or node-role component in the path at all. `save_cache()` only runs when `SLURM_NODEID == 0`, so the tarball only ever captures the *head* node's compiled artifacts. `restore_cache()` has no such gate — it's called unconditionally from `run-head-vllm.sh`, `run-worker-vllm.sh`, *and* `ray-setup.sh`, on every node, every run. Net effect: any node in any run — head or worker, regardless of which physical machine it actually is — gets the exact same tarball restored onto it, built from whatever one specific head node compiled in some earlier run, with zero validation that the current node is even compatible. On a shared SLURM queue where the same job name can land on different physical GH200 units run to run, this is a real cross-node cache-poisoning path: a worker node can silently receive cubins compiled against a different machine's driver/microcode. Found while investigating MiniMax-M3 instability (see below) — not yet confirmed as the direct cause of any specific observed crash, but a real, live structural bug independent of that investigation. Suggested fix: key the tarball by hostname too, or gate `restore_cache()` on only restoring onto the same node identity it was saved from.

- **`login_force_cancel` test failure — needs confirmation, not yet root-caused.** `tests/bash/sandboxed/test-login-handoff.sh`'s `login_force_cancel` fails because `ivllm-cancel.sh -f` logs `"not possible to force cancel job owned by root"` and never calls `scancel`. The test's fixture lockfile sets `"user":"root"` but the sandbox actually runs as a non-root user, so this may just be an ownership check correctly doing its job against a stale test fixture (similar in flavor to the `2775` permissions-scheme staleness above) rather than a genuine bug — hasn't been dug into further.

## Mitigated (root cause unconfirmed)

- **Nemotron-3-Ultra-550B multinode (Ray, TP=8 across 2 nodes) hung reliably within minutes of every real run, 2026-08-04/05.** Every attempt (dozens, across the `multinode ray support` work) died the same way: `vLLM` served startup/warmup and a handful of real requests fine, then `EngineCore` logged `"No available shared memory broadcast block found in 60 seconds"` five times (~300s) before `TimeoutError: RPC call to sample_tokens timed out` → `EngineDeadError`.

  **Investigation path** (see conversation history for full detail; summarised here for anyone picking this back up):
  1. Initial log analysis found Triton kernels (`_zero_kv_blocks_kernel`, `_compute_slot_mapping_kernel`, `_causal_conv1d_fwd_kernel`, `eagle_*`) JIT-compiling during inference near the hang, matching several open vLLM GitHub issues (#45198, #43009) about warmup-coverage gaps under TP≥2. Testing with `speculative-config` disabled showed the hang moved *earlier* (into ivllm's own startup warmup) rather than disappearing — ruling out MTP/speculative-decoding as the cause, since the same core KV-cache/Mamba kernels are used with or without it.
  2. Added `IVLLM_RUNTIME_DEBUG` / `IVLLM_DEBUG_LEVEL` env-var-gated instrumentation to `wait_report()`/`report_memory()` (`src/engine/lib/utils.sh`) — extends periodic Cache/RAM/Top logging through the `running` phase (not just `initialising`), and at higher debug levels adds a per-GPU `nvidia-smi` snapshot and `py-spy dump --nonblocking` stack traces of every vLLM/Ray worker process, written to a persistent per-node file under the shared job dir (`$PROJECTDIR/engine/jobs/<job>/debug/pyspy-node<N>.log` — deliberately not `$localdir`, which is node-local tmpfs, invisible to other nodes, and wiped on shutdown).
  3. A real hung run captured with this instrumentation showed something different from the Triton-JIT theory: **all 8 worker ranks, both nodes, frozen at the identical frame** — `torch.cuda.graphs.CUDAGraph.replay()`, inside the MTP (`nemotron_h_mtp`) draft model's forward pass (`propose_draft_token_ids`) — no compilation involved, JIT had finished minutes earlier. The GPU-utilisation snapshot was the deciding evidence: 7 of 8 GPUs pegged at 100% (consistent with legitimately spinning inside a stuck NCCL collective) but **rank TP0/EP0 on the head node sat at 0%** the entire ~4-minute hang — everyone else waiting on it, it doing nothing.
  4. This matches [vLLM issue #46097](https://github.com/vllm-project/vllm/issues/46097) almost exactly: a multi-node TP CUDA-graph-replay NCCL collective deadlock, independently reported on a different model, diagnosed there as "the ranks are likely not in the same collective instance" — a tensor-parallel control-flow divergence, not a compile-timing issue. That thread's own discussion (read via the GitHub API, since `gh` isn't authenticated in this environment and the GitHub web UI doesn't render comments through `WebFetch`) found the divergence to be **NCCL-build-specific, not version-specific**: two builds of the identical version string (`2.28.9`) — a `pip` wheel vs. the OS vendor's `apt` package — behaved completely differently (deadlock vs. stable), identifiable only by SHA256/Build ID, not by version string, log banner, or `NCCL_VERSION` env var (all shown to be unreliable/stale in that thread).
  5. Built `design/prototype/nccl-probe.sh` (non-invasive, read-only) to check Isambard's actual situation: confirmed **torch/vLLM's default NCCL is the bundled `nvidia-nccl-cu12` pip wheel (2.28.9)**, not NVHPC 26.3's bundled copy (2.29.3) or anything from the `brics/nccl` module (which turned out to provide no `libnccl.so` at all — likely just the `aws-ofi-nccl` plugin). Confirmed via direct `ncclGetVersion()` ctypes calls (not `torch.cuda.nccl.version()`, which turned out to be **misleading in practice** — it kept reporting the old version even after the on-disk file was replaced and reloaded, implying it's a value baked into the torch wheel at torch's own build time, not a live query). Also confirmed `LD_PRELOAD`-ing an alternative NCCL does **not** override torch's own bundled copy — torch loads its own file by absolute path regardless, so both end up mapped and torch's own copy is what's actually used.
  6. Upgraded the venv's `nvidia-nccl-cu12` to `2.30.4` (available directly on PyPI — no source build needed) — the one build a third party in the #46097 thread reports as stable under sustained multi-node TP load for days. Re-ran `nccl-probe.sh`: confirmed via `ncclGetVersion()` that this is genuinely what loads now, and added a 2-node transport-selection smoke test (`NCCL_DEBUG=INFO` + a real `torch.distributed` `all_reduce` across both nodes) to check the upgrade doesn't break Isambard's Slingshot integration — confirmed `NET/OFI Selected Provider is cxi` (Cassini/libfabric genuinely in use, not a silent TCP fallback) and a mathematically correct `all_reduce` result, so the existing `aws-ofi-nccl 1.8.1-aws` plugin is compatible with the new core NCCL.

  **Fix applied**: `nvidia-nccl-cu12==2.30.4` is now pinned in `slurm-vllm-setup.sh` (added after the vLLM install step, unconditionally so it applies to pre-existing venvs too).

  **Status**: `examples/nemotron-3-ultra-550B-A55B-FP8.yaml` promoted from `lifecycle: experimental` to `operational` (`logs/ntron550/20260805_134500_working/` — a real ~15-minute interactive session, clean user-cancel shutdown, no hang) on the strength of this evidence, but **the root cause is not fully proven** — no long soak test has been run, and the mechanism by which a specific NCCL build causes the TP rank divergence (rather than merely correlating with it) was never identified even in the upstream issue thread. If the hang recurs, re-enable `IVLLM_RUNTIME_DEBUG: 1` / `IVLLM_DEBUG_LEVEL: 2` (or `3`) in the job's `env:` block and check `debug/pyspy-node*.log` for the same frozen-rank signature before assuming this is unrelated.

- **MiniMax-M3-FP8-dynamic under hybrid TP=4×DP=2 (2×4-GPU nodes) — blocked on a Triton kernel crash after clearing three separate, confirmed bugs.** `examples/minimax-m3.yaml`, 2026-08-07. Goal: get MiniMax-M3 (427B/26B-active MoE, MSA sparse attention, EAGLE3 speculative decoding) serving across 8 GPUs on 2 nodes. Still not working end-to-end, but the investigation surfaced and fixed/worked-around three genuinely separate, reusable bugs along the way — worth reading in full before re-attempting.

  **Investigation path** (logs under `logs/mmax3/`, timestamps below; see conversation history for full detail):
  1. Early attempts (`20260807_10*`) hit a startup feasibility `ValueError` (requested KV cache larger than available) and separately an `AssertionError: DeepEP v2 (ElasticBuffer) not available` when trying `all2all-backend: deepep_v2` — the installed `deep_ep` is UCCL-EP's compatibility wrapper (`vendor/uccl`), confirmed to genuinely lack the v2 `ElasticBuffer` API, not a version-string mismatch. Settled on `all2all-backend: allgather_reducescatter` instead, which supports all quantization types.
  2. A GPU OOM during vLLM's flashinfer-autotune warmup dummy-run (`kernel_warmup.py` → `flashinfer_autotune` → `_dummy_run`) went **completely undetected by ivllm** — the process tree wedged (an exception inside `worker_busy_loop` was caught internally by vLLM and didn't kill the process) rather than crashing cleanly, so `wait_report()`'s death-detection never fired, and `monitor_head()` had no active liveness check during `initialising` at all (only during `running`, via idle-timeout log-grepping) — the job sat there until manually cancelled, and since `tidy_up()`'s `SIGUSR2`/201 (user-cancel) path never calls `capture_job_diagnostics()`, nothing was even auto-archived. Fixed two real ivllm gaps as a result: added `IVLLM_CRASH_INDICATORS` (`torch.OutOfMemoryError`, `EngineDeadError`, `WorkerProc hit an exception`) log-message detection to `monitor_head()`, and — after a first version placed that check *after* the `initialising` branch, where it was structurally unreachable since every path through that branch ends in `continue`/`return` — relocated it to run unconditionally near the top of the loop, before the status-specific branches. Confirmed working in `20260807_140029`: crash detected and diagnostics auto-archived while still `initialising`, no manual intervention needed.
  3. The OOM itself kept recurring across many gpu-memory-utilization/max-model-len tuning attempts despite `enable-flashinfer-autotune: false` being set, because **that setting was never actually taking effect** — root-caused to a separate vLLM bug (see "vLLM's `--config <file>.yaml` loader silently drops boolean `false` values" above in this same list) that silently drops any bare `key: false` yaml line for a flag whose real default isn't already `False`. Worked around by wrapping it as JSON instead: `kernel-config: '{"enable_flashinfer_autotune": false}'`. Confirmed fixed in `20260807_140029` (`enable_flashinfer_autotune=False` in the effective config dump) — the autotune-warmup OOM has not recurred since.
  4. With the OOM gone, hit `ValueError: Flashinfer allreduce is not supported for multi-node allreduce with 'trtllm' backend` — `vllm-env.sh:77` hardcodes `VLLM_FLASHINFER_ALLREDUCE_BACKEND=trtllm` for every job (comment: "Force standard NCCL for Slingshot stability"). Traced to `get_fi_ar_workspace()` (`vllm/distributed/device_communicators/flashinfer_all_reduce.py`) checking the *whole deployment's* node count (`get_node_count()`) instead of the specific TP group's own node span, even though it's already passed that exact group (`group=get_tp_group().device_group`, from `fused_allreduce_gemma_rms_norm.py`) — confirmed via `vendor/vllm` source and cross-checked against real logs from both this model and `qwen35-397` (same hybrid TP-node-local/PP-cross-node shape, same crash). Also confirmed via `vendor/vllm` that `deepseek_v32/nvidia/fused_ops.py` and `minimax_m3/amd/model.py` use the same fused op, so this affects those too. **Reported upstream to vllm-project/vllm.**
  5. Tried `VLLM_FLASHINFER_ALLREDUCE_BACKEND=mnnvl` as a workaround (routes around the buggy guard, which only fires for `backend=="trtllm"`) — this cleared the `ValueError`, but crashed harder: a genuine CUDA context failure, `CUDA error: an illegal memory access was encountered` from `ProcessGroupNCCL`'s watchdog thread across all ranks (`20260807_140029`'s follow-up, `20260807_145652`). Confirms `mnnvl` is genuinely unsafe on Isambard's Slingshot fabric (no real inter-node NVLink/NVSwitch for its multicast workspace) — not just unsupported, actually hardware-incompatible — which is almost certainly *why* `trtllm` was hardcoded as the default in the first place.
  6. Patched the installed vLLM directly instead: `design/prototype/patch/hybrid-trtllm.sh` changes `get_fi_ar_workspace()`'s guard to `_node_count(get_tp_group().cpu_group) > 1` — using vLLM's own existing `_node_count()` helper, scoped to the TP group instead of the whole deployment (must use `.cpu_group`, not `.device_group`; `_node_count()`/`in_the_same_node_as()` assert a non-NCCL group). See `design/prototype/patch/README.md` for full usage/caveats. This worked: `20260807_151912` shows `trtllm` selected with no crash, full engine init (27-37s), `/health` up, and the warmup request running real inference far enough to JIT-compile a long chain of MiniMax-M3's custom kernels.
  7. New crash, further in than anything before: `RuntimeError: Triton Error [CUDA]: an illegal memory access was encountered` inside MiniMax-M3's own sparse-attention decode kernel (`vllm/models/minimax_m3/common/ops/sparse_attn.py:511`, `_gqa_sparse_decode_kernel`), failing specifically in Triton's `_init_handles()` → `driver.active.utils.load_binary()` — i.e. while loading the *compiled kernel binary* into the CUDA context, not inside the kernel's own compute logic. That's more consistent with an already-corrupted CUDA context than a plain indexing bug in this one kernel, but not conclusive — only DP0's ranks show it in the one log captured (`20260807_151912`), which is mildly odd for a deterministic kernel bug but could just be incomplete capture.

  8. Drafted a second, complementary patch — `design/prototype/patch/diffs/skip-flashinfer-fusion-multinode.v0.25.1.patch` + generic `apply-vllm-patch.sh` tool — making `_can_use_flashinfer()` return `False` immediately whenever the TP group spans >1 node, so a genuinely cross-node TP group (TP=8×Ray, no DP split) never attempts either flashinfer backend at all and always takes the safe unfused fallback. See `design/prototype/patch/README.md`.
  9. Tested TP=8×Ray with patch (8) applied, using the **official** `MiniMaxAI/MiniMax-M3-MXFP8` checkpoint (ruling out the fp8-dynamic-vs-MXFP8 checkpoint format as a variable too). **Confirms step 7 was independent of allreduce backend**: the traceback shows the crash happening inside the patched, safe fallback path itself (`fused_allreduce_gemma_rms_norm.py:152` → plain `tensor_model_parallel_all_reduce` → `ncclAllReduce` → `RuntimeError: NCCL error: unhandled cuda error`) — flashinfer/trtllm/mnnvl were never touched. Combined with step 7's Triton-kernel-load crash and step 5's NCCL-watchdog crash, the same illegal-memory-access family has now surfaced through three unrelated call sites across three configurations (fp8-dynamic hybrid+trtllm-patch, fp8-dynamic hybrid+mnnvl, official-MXFP8 TP8×Ray+patch-8). Root cause is very likely a genuine bug in one of MiniMax-M3's own custom Triton kernels (sparse-attention/indexer/eagle — all JIT-compiling in the seconds before every one of these crashes), corrupting the CUDA context; whichever CUDA/NCCL call runs next just surfaces the resulting garbage state. No longer considered ambiguous — this is independent of allreduce backend, DP/Ray topology, and checkpoint quantization format.
  10. New, separate `monitor_head()` gap found while diagnosing (9): the crash-indicator check (added in step 2) is correctly positioned at the top of the loop, but once execution enters the `initialising` branch's warmup-request-sending code it stays inside that nested retry loop (5 attempts, `sleep 10` between) and never returns to the top of the outer loop to re-check — so a crash occurring *during* an in-flight warmup request is invisible to it. In (9) this meant detection fell back to the slower path (vLLM's own ~5-minute internal RPC-timeout self-shutdown, then `wait_report()` catching the resulting exit-code-0 process death — which `tidy_up()` correctly flags as anomalous, hence "shutdown was not particularly clean" but diagnostics were still captured). Not yet fixed; would need the crash-indicator check pulled into (or polled from) the warmup-retry loop itself, not just the outer one.

  11. Root-caused a plausible upstream explanation for the step 7/9 crash family: found `vllm-project/vllm` issue [#48603](https://github.com/vllm-project/vllm/issues/48603) — "MiniMax M3 Triton path misinterprets token-major top-k buffer" — reporting the exact same `RuntimeError: Triton Error [CUDA]: an illegal memory access was encountered` signature, in the same kernel family (`common/indexer.py`, `common/ops/index_topk.py`, `_topk_index_kernel`). Root cause per the issue: `topk_indices_buffer` is allocated token-major (`[tokens, heads, topk]`) but the Triton indexer/sparse-attention kernels read it head-major. The actual merged fix is PR [#49149](https://github.com/vllm-project/vllm/pull/49149) (merged 2026-07-25, commit `d1a8ba63d9d2bb51ebf60dd5ea1463cf61c70cea`) — an earlier attempt, PR #48604, was closed unmerged/needs-rebase. Confirmed directly against source: **v0.25.1** (tagged 2026-07-12) predates the fix; **v0.26.0** (released 2026-07-27) has it — `nvidia/model.py` there allocates the buffer token-major with an explicit comment matching the fix description.
  12. Upgraded to v0.26.0 (fresh venv via `slurm-vllm-setup.sh`). Hit an unrelated, optional-dependency build failure along the way — NIXL's `python3 -m build --no-isolation` step fails its own "Getting build dependencies for wheel" check because `torch==2.11.*` declares an exact pin on `nvidia-nccl-cu12==2.28.9`, which this project deliberately overrides to `2.30.4` earlier in the same script (the Nemotron NCCL fix). NIXL doesn't actually use NCCL at all (UCX/libfabric-based), so this is a pure metadata-check collision; fix is `--skip-dependency-check`/`-x` on that `python -m build` call (not yet applied — skipped NIXL/humming/hpc-ops for this install, none of which the current configs use anyway). Then hit a **second, unrelated bug**: some early logs after the upgrade showed the driver process (`EngineCore`) running under `/vllm/0.25.1/...` while Ray worker actors ran under `/vllm/0.26.0/...` — two different vLLM installs mixed within the same job. Root-caused to the `ray-run-vllm.sh` variable-ordering bug (see its own `Known Issues` entry above) — fixed by hoisting the `IVLLM_JOB=${1:?...}` assignment to the top of the script; confirmed fixed in all subsequent runs (`grep -o "vllm/0\.2[56]\.[01]"` shows only one version per log from `20260807_191038` onward).
  13. With 0.26.0 + correct version resolution, re-applied `hybrid-trtllm.sh`'s node-count-scoped patch and tried a *genuinely* cross-node TP=8×Ray config (no DP split at all, unlike steps 4-9's TP=4×DP=2 hybrid). Hit the *original* `trtllm` `ValueError` again — but this time correctly, not a bug: for TP=8 with no DP, the TP group itself genuinely spans both nodes, so even the *patched* `_node_count(group) > 1` check correctly rejects `trtllm` (it fundamentally cannot do multi-node allreduce; the patch only fixes the case where the TP group is node-local but the deployment isn't). Confirmed via source this is unrelated to Ray or topology generally — Nemotron-3-Ultra runs TP=8×Ray across 2 nodes fine because its model code never calls `fused_allreduce_gemma_rms_norm`/`get_fi_ar_workspace` at all (no such log line ever appears in its logs); the guard is simply unreachable code for that model.
  14. Since genuine cross-node TP has no working flashinfer backend at all (`trtllm` correctly refuses it, `mnnvl` crashes the CUDA context on Slingshot per step 5), drafted a third, simpler patch: `design/prototype/patch/diffs/disable-flashinfer-env.v0.25.1.patch` — adds an `IVLLM_DISABLE_FLASHINFER=1` env-var check to the *top* of `_can_use_flashinfer()` (`fused_allreduce_gemma_rms_norm.py`), unconditionally routing to the existing safe fallback (`tensor_model_parallel_all_reduce` + plain `GemmaRMSNorm`) regardless of node topology. Opt-in per job via the yaml `env:` block, so it doesn't affect other models/jobs sharing the venv. Verified byte-exact apply/revert against `vendor/vllm`. Confirmed firing correctly in `20260807_191731`'s log (`"IVLLM_DISABLE_FLASHINFER=1 — skipping flashinfer fused allreduce+RMSNorm"`), and again after being separately re-applied to the fresh 0.26.0 venv (patches must be re-run per version — they don't carry over between installs).
  15. With flashinfer fully bypassed, hit a **different failure**: a plain `TimeoutError: RPC call to sample_tokens timed out` (no crash signature at all) at `multiproc_executor.py`'s default `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS=300`. ## Resolved

- **Console log tailing dropped/garbled lines** (missing `-n` history window on `tail -f`, raw `\r` progress bars overwriting console lines, chunk-not-line stdout echoing in `runRemote`, and a racy double-tail handoff between job startup and `watchLog`). Fixed by: explicit `-a`/from-now flag on `ivllm-show-log.sh` replacing the ambiguous default `tail -f` window; `stdbuf -oL tr '\r' '\n'` normalization in both tail pipelines; line-buffering in `SshRemoteOps.runRemote()`; and removing `requestStart()`'s own log monitor in favour of a single `watchLog()` call in `cmdConnect`/`cmdCancel` gated by status polling (`isStarting`/`isStopped`) instead of log-text markers.

- **`wait_report()` couldn't detect or propagate a crashing vLLM process's real exit code** (`src/engine/lib/utils.sh`). `wait_report()` is the last command in `run_head_vllm.sh`; its own exit status becomes the script's exit status, which `srun` mirrors, which `wait_all`/`setup_traps`'s EXIT trap (`tidy_up`) receives as the real crash/exit code. The old loop only ever did `kill -0 "$pid"` — never `wait "$pid"`. Since `$pid` is a direct child of that same shell, once it exits it becomes a zombie, and `kill -0` still succeeds on a zombie (the PID stays allocated until the parent reaps it) — so the loop could never reliably notice death, let alone capture the real exit code. In practice this meant a genuine crash was never caught via the fast, correct exit-trap path, and instead surfaced only later via `monitor_head`'s independent idle-timeout detection, which routes through `tidy_up`'s `201` ("user cancel or idle timeout") branch — a branch that does **not** call `capture_job_diagnostics`. Net effect: crash diagnostics were silently never captured, misreported as an idle shutdown instead.
  Fixed by checking `/proc/$pid/stat`'s state field for `Z` (zombie) instead of trusting `kill -0`, then doing a final `wait "$pid"; return $?` to reap it and propagate the real exit code.
  Verified by `tests/bash/sandboxed/test-wait-report.sh` (`wait_report_propagates_crash_exit_code`, `wait_report_propagates_clean_exit_code`) — both currently pass against the fixed code.

- **`copyDirectory()` didn't reliably make the bootstrapped remote engine directory group-writable** (`src/ops/SshRemoteOps.ts`). Two related problems, found while investigating a report that one user's `ivllm` run left `$projectDir/engine/lib` un-writable for other users in the same HPC project group:
  1. `rsync -a` (archive mode, which implies `--perms`) copies the *local* machine's exact permission bits onto the shared remote directory on every bootstrap sync (`IsambardBareMetalBackend.bootstrap()` calls this unconditionally). Whoever's local umask/checkout happened to be more restrictive would silently clobber the shared directory's group-writability for everyone else.
  2. Directories and files needed different fixes. Directories: `--no-perms --no-owner --no-group` (stop copying source permission bits) + `--rsync-path 'umask 002 && rsync'` (force the *receiving* rsync process's umask, scoped only to this transfer via `--rsync-path`, not global shell config) is sufficient — a newly-created directory gets a fresh default request (`0777`) that a `002` umask correctly masks to `0775`. Regular files are different: without `--perms`, rsync (like plain `cp` without `-p`) uses the *source file's own mode bits* as the base request, and a umask can only strip bits from that, never add ones the source lacked — so a file that's locally `644` (no group-write — exactly what a fresh `git clone` produces under a normal `022` umask, since git only tracks the executable bit) stayed `644` on the destination no matter what umask the `--rsync-path` trick forced. Confirmed as standard POSIX copy semantics (reproduces identically with plain `cp`), not an rsync quirk, and confirmed to matter in practice only when the pushing machine's local checkout isn't already group-writable (invisible in an environment where it happens to be, e.g. this sandbox's own `775`/`664` files — masking the gap during earlier real-world validation).
  Fixed by following the rsync (on `'up'` transfers only) with an explicit `chmod -R g+rwX "${remotePath}"` over the same SSH connection — deterministic and independent of source mode or any umask timing, closing the gap for both directories and files uniformly. `copyFile()` (used for uploading a job's `vllm.yaml`) was separately re-implemented to stream via `umask 002 && cat > remoteFile` instead of `scp` (which has no `--rsync-path`-equivalent hook), so it was never subject to the file-level gap.
  Verified by `tests/unit/SshRemoteOps.test.ts` (all 3 tests passing): `copyDirectory` leaves both the destination directory *and* files group-writable even under a restrictive local umask with a source file that itself lacks the bit, and `copyFile` likewise.

- **`bun:test` cannot reliably exercise umask-dependent child-process behaviour** (testing-infrastructure finding, not a product bug — kept here for the record since it cost real investigation time and could recur). While building the `copyDirectory` permission tests above, a test asserting group-write via the `--rsync-path 'umask 002 && rsync'` mechanism *alone* (before the `chmod -R g+rwX` fix existed) consistently failed under `bun test` but passed when the identical code (same `SshRemoteOps` class, same fake-`ssh`-on-PATH fixture used in `tests/unit/SshRemoteOps.test.ts`, same `process.umask(0o022)` simulation) was run via plain `bun run` instead — and the `bun run` result matched real Isambard behaviour. Conclusion: Bun's test runner (`1.3.14`) does something that breaks umask inheritance from a test's `process.umask()` call down to a spawned child process; the exact internal mechanism wasn't identified further. This is no longer blocking anything — the shipped fix (explicit `chmod -R g+rwX`) is deterministic and untroubled by this, so all three tests in `tests/unit/SshRemoteOps.test.ts` pass reliably under `bun:test`. Documented here in case a *future* test ever needs to depend on umask propagating to a spawned child under `bun test` — that will hit the same wall.
